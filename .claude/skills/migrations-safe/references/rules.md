# Rules of migration-lint

Load this when a finding needs explaining or fixing. One row per rule the linter can emit; the test suite
checks this table against the rule registry in `scripts/lib/rules.mjs`.

Levels: `error` fails the run by default; `warning` fails only with `--fail-on warning` (or `--strict`) or when
the rule is named in `--fail-on`. Lock rules are errors on a table that already exists (not created earlier in
the same file, or in an earlier new migration of the branch when `--history` is used).

Silencing is a recorded decision: `-- migration-lint: allow <rule>[, <rule>] -- <who, when, why>` on its own
comment line before the statement (or trailing it), or `allow-file` for the whole file. The comment must start
with `migration-lint:`, name known rules and give a reason; otherwise it silences nothing and raises
`invalid-directive`.

| Rule | Level | Why it breaks | Correct | Wrong |
|---|---|---|---|---|
| `drop-table` | error | Data gone; running code still reads the table | Contract step after a release that stopped using it; verified backup; `allow` with who/when/backup | Dropping in the release that stops using it; "it's unused" without grepping code and reports |
| `drop-column` | error | Data gone; running code selects or inserts the column | Same as `drop-table`; tell the ORM to ignore the column one release before (`ignored_columns`, `@Transient`) | Dropping in the same release |
| `drop-schema-cascade` | error | Drops every object in the schema | Drop the objects one by one in contract steps, or approve with a backup | `CASCADE` "to make it pass" |
| `drop-materialized-view` | error | The stored result is gone and readers break | Contract step after readers moved; recreate and refresh in the same release if it is only being redefined | Drop and recreate in one transaction on a busy view |
| `truncate` | error | Every row deleted | Verified backup and recorded approval | Truncate to "reset" a table that production fills |
| `delete-all` | error | `DELETE` without `WHERE`, or with an always-true one, removes every row | Batched delete by key range, outside the DDL migration | `DELETE FROM t` in a migration |
| `update-all` | error | One transaction over the whole table: long locks, bloat, replica lag. A `WHERE col IS NULL` that selects every row to fill counts | Backfill outside the migration, by key range (`WHERE id > $last ORDER BY id LIMIT 1000`), idempotent, resumable | `UPDATE t SET ...` in the migration |
| `rebuild-drops-column` | error | A SQLite table rebuild (create `new_t`, `INSERT ... SELECT`, drop, rename) whose new table lacks a column of the old one, or whose `INSERT` does not copy it, silently loses its data | Copy every column the table keeps; for an intended drop, `allow` with the backup. The old table is known from earlier migrations of the same folder or from `--schema` | Trusting the generated rebuild |
| `prisma-data-loss-warning` | error | Prisma writes what its SQL loses in a `/* Warnings: */` comment; those lines are findings (error for drops, casts and lost data, warning for the rest) | Read each warning; split the change into expand/contract; for an intended loss `allow` with the backup | Deleting the comment |
| `rename-column` | error | Old code uses the old name the second the migration commits | Add new, write both, backfill, switch reads, drop old later | `RENAME` in one step "because it's fast" |
| `rename-table` | error | Same as `rename-column`; includes MySQL `RENAME TABLE` and `SET SCHEMA` | New table (or a view with the old name) and move readers first | One-step rename |
| `change-column-type` | error | Rewrites the table under an exclusive lock; narrowing fails or truncates real data. MySQL `MODIFY` and `CHANGE` count | New column of the new type, backfill, switch, drop old. Safe in place: `varchar(n)` to `varchar(m>n)` or `text` in PostgreSQL: `allow` with that reason | `USING col::int` on a populated table in one step |
| `not-null-without-default` | error | Fails on a populated table (SQLite even on an empty one); old code's INSERTs break | Add nullable, backfill, then enforce; or a constant default if one is truly right | A fake default (`''`, `0`, `'unknown'`) to make it pass |
| `set-not-null` | error | Full scan under ACCESS EXCLUSIVE (PostgreSQL) | `ADD CONSTRAINT c CHECK (col IS NOT NULL) NOT VALID`, next migration `VALIDATE CONSTRAINT c`, then `SET NOT NULL` (PG 12+ uses the check, no scan) and drop the check. The last step is not flagged when the same file validates the constraint or drops a `*_not_null` one; otherwise `allow` it saying the validated check exists | `SET NOT NULL` directly on a big table |
| `constraint-without-not-valid` | error | FK or CHECK validates every row holding a lock that blocks writes | `... NOT VALID`, then `VALIDATE CONSTRAINT` in its own migration | Disabling triggers or the FK to speed it up |
| `constraint-builds-index` | error | UNIQUE and PRIMARY KEY build their index under ACCESS EXCLUSIVE | `CREATE UNIQUE INDEX CONCURRENTLY`, then `ADD CONSTRAINT ... USING INDEX`; find duplicates first | Deleting "duplicates" inside the migration |
| `primary-key-using-index` | error | `ADD PRIMARY KEY ... USING INDEX` still sets the columns NOT NULL, scanning the table unless they already are (or have a validated `IS NOT NULL` check) | Enforce NOT NULL first as in `set-not-null`; the rule is quiet when the file does it before | Assuming `USING INDEX` makes it instant |
| `index-without-concurrently` | error | Writes blocked for the whole index build | `CREATE INDEX CONCURRENTLY` in its own file, in the runner's no-transaction mode; if it fails, drop the `INVALID` index and retry | Building it at night and hoping |
| `drop-index-without-concurrently` | error | `DROP INDEX` takes ACCESS EXCLUSIVE on the table | `DROP INDEX CONCURRENTLY`, no transaction | Plain `DROP INDEX` |
| `volatile-default` | error | A volatile default (`random()`, `gen_random_uuid()`, `uuid_generate_v4()`, `clock_timestamp()`, `nextval`) rewrites the table under ACCESS EXCLUSIVE. `now()` and `CURRENT_TIMESTAMP` do not (PG 11+) and string literals are not calls | Add the column without default, `ALTER ... SET DEFAULT`, backfill in batches | Adding it with the default |
| `rewriting-column` | error | `serial`, identity and stored generated columns rewrite the table | Add a plain column, backfill, then attach the sequence or identity | Adding `serial` to a big table |
| `mysql-no-algorithm` | warning | MySQL silently falls back to a table COPY with locks | `ALGORITHM=INSTANT`, or `INPLACE, LOCK=NONE`, so it fails instead; COPY on a big table: gh-ost | Trusting the default |
| `mysql-algorithm-unsupported` | error | An explicit `ALGORITHM=` the operation or the server version cannot honour: the statement fails at run time (ERROR 1845 or 1846; 1800 where `INSTANT` is unknown; 1221 for `INSTANT` with a `LOCK` clause). `INSTANT` does not exist before MySQL 8.0.12 / MariaDB 10.3; adding a column at `FIRST`/`AFTER` and dropping a column are instant from 8.0.29 (MariaDB 10.4), renaming from 8.0.28; indexes, primary keys, foreign keys and rebuilds are never `INSTANT`; a column redefinition is only when just the default changes (MySQL; the earlier definition comes from the migrations read, and is a warning when unknown; MariaDB 10.4+ also runs charset, collation and position changes), and `ENUM`/`SET` appends must keep nullability. `INPLACE` cannot drop a primary key without adding one and cannot add a foreign key with `foreign_key_checks=1`; `CONVERT TO CHARACTER SET` with `INPLACE` is a warning (it runs for unindexed utf8mb3 columns) | Pick the algorithm the operation supports (see the table in [mysql.md](mysql.md)); for a big table that needs `COPY`, gh-ost or pt-online-schema-change. Set `--mysql-version` so the check matches production | Dropping the `ALGORITHM` clause so it "works": the server then picks `COPY` silently |
| `mysql-lock-wait-timeout` | warning | DDL waits for the table's metadata lock behind every open transaction, even an idle one, and every later query on the table queues behind the DDL. `SET SESSION`, `SET STATEMENT` and MariaDB's `WAIT n` count; setting it after the first DDL does not | `SET SESSION lock_wait_timeout = 5;` before the first DDL on an existing table (also `RENAME TABLE`, `OPTIMIZE TABLE`, `CREATE`/`DROP INDEX`), retry with backoff | A long timeout so it does not fail |
| `mysql-add-foreign-key` | error | With `foreign_key_checks=1` adding a foreign key to an existing table only works with `ALGORITHM=COPY`: the table is copied while writes are blocked. `INPLACE` needs `foreign_key_checks=0`, which also skips validating existing rows. Quiet when the file switches the setting off before the statement | Check orphans with a query, `SET SESSION foreign_key_checks=0`, `ALTER ... ADD FOREIGN KEY, ALGORITHM=INPLACE, LOCK=NONE`, set it back to 1. gh-ost does not support foreign keys; pt-online-schema-change needs `--alter-foreign-keys-method` | Leaving checks on and trusting `LOCK=NONE` |
| `mysql-fk-implicit-index` | warning | A foreign key with no index on its columns makes MySQL create one inside the same ALTER, lengthening the lock. The linter knows the indexes of tables created or altered in the migrations it reads, so allow it when the index exists elsewhere | `ADD INDEX` first (`INPLACE`, `LOCK=NONE`), then the key | Letting the key create its index |
| `mysql-fulltext-spatial-index` | error | `FULLTEXT` and `SPATIAL` builds block writes (`LOCK=NONE` is rejected); the first `FULLTEXT` index also rebuilds the table unless `FTS_DOC_ID` exists | Shadow table with gh-ost or pt-online-schema-change, or a recorded maintenance window | `LOCK=NONE` hoping for the best |
| `mysql-drop-primary-key` | error | Dropping a primary key without adding one in the same statement is `COPY` only, with writes blocked | Replace it in one statement (`DROP PRIMARY KEY, ADD PRIMARY KEY (...)`, `INPLACE`), or gh-ost | A separate `DROP PRIMARY KEY` migration |
| `mysql-add-primary-key` | warning | Rebuilds the whole table in place: concurrent DML is allowed but disk use doubles and the metadata lock waits behind long transactions; nullable columns need `NOT NULL` first and duplicates fail at the end | Off-peak with `LOCK=NONE` after checking NULLs and duplicates, or gh-ost | Adding a key on a table with NULLs and trusting it |
| `mysql-charset-conversion` | error | `CONVERT TO CHARACTER SET` and column `CHARACTER SET`/`COLLATE` changes rewrite the text columns with writes blocked; `utf8`/`utf8mb3` to `utf8mb4` grows keys (767-byte limit on `COMPACT`/`REDUNDANT` rows, 3072 on `DYNAMIC`) and joins against columns with another collation stop using their index | gh-ost or pt-online-schema-change; keep collations equal on both sides of every join and foreign key | Converting the whole table in one `ALTER` on a hot table |
| `mysql-enum-change` | error | Appending members to the end of an `ENUM`/`SET` is instant while the storage size stays the same (`ENUM` up to 255 members, `SET` per 8); inserting, reordering or removing members renumbers stored values and copies the table with writes blocked. A warning when the previous definition is unknown (it is read from `CREATE TABLE` and `ALTER` statements of the migrations) | Append only, at the end, with `ALGORITHM=INSTANT`; a new column or lookup table for anything else | Reordering "to keep it alphabetical" |
| `mysql-table-rebuild` | warning | `OPTIMIZE TABLE`, `ALTER TABLE ... FORCE`, `ENGINE=InnoDB` and `ROW_FORMAT`/`KEY_BLOCK_SIZE` changes rebuild the table: online, but every page is copied, disk use doubles, replicas replay it serially and the metadata lock waits at both ends. `OPTIMIZE TABLE` takes no `ALGORITHM` or `LOCK` clause | Off-peak, under `lock_wait_timeout`, or gh-ost; reset the instant row-version count on purpose | `OPTIMIZE TABLE` in a migration "to reclaim space" |
| `mysql-column-position` | warning | `MODIFY`/`CHANGE` with `FIRST`/`AFTER` reorders columns and rebuilds the table; `ADD COLUMN ... FIRST/AFTER` is only instant from MySQL 8.0.29 (before, only as the last column) | Leave the column where it is, or add it last | Adding "after id" for readability |
| `mysql-instant-row-versions` | warning | InnoDB keeps 64 row versions per table for instant `ADD`/`DROP COLUMN`; at the limit `ALGORITHM=INSTANT` fails (ERROR 4092). The count is the instant add/drop statements per table in the files it read (earlier files of the folder are replayed, also in `--history`), only on MySQL 8.0.29+ where the limit exists, not counting statements that also add an index; reset by a rebuild (`FORCE`, `OPTIMIZE`, an `INPLACE`/`COPY` add). It is reported from the 56th: a margin the linter chose, because it cannot see statements run by hand or by other branches. Not applied to MariaDB | Check `INFORMATION_SCHEMA.INNODB_TABLES.TOTAL_ROW_VERSIONS`; rebuild the table off-peak before the next instant change | Retrying the failed `ALTER` |
| `mysql-change-column-rename` | warning | `CHANGE COLUMN old new <definition>` restates the definition to rename: any difference from the real one becomes a type or nullability change (a table copy) | `RENAME COLUMN old TO new` (MySQL 8.0, MariaDB 10.5.2; instant from 8.0.28). The rename itself still needs expand/contract (`rename-column`) | `CHANGE` with a definition typed from memory |
| `mssql-add-not-null-default` | error | SQL Server: adding a NOT NULL column with a DEFAULT (or a nullable one with `WITH VALUES`) writes the default into every row under Sch-M on every edition except Enterprise/Azure, and on any edition when the default is not a runtime constant (`NEWID()`, `NEXT VALUE FOR`, `RAND()`) | Add the column NULL (metadata-only), backfill in batches, then enforce | `ADD c int NOT NULL DEFAULT 0` on a big table under Standard |
| `mssql-alter-column` | error | `ALTER COLUMN` without `WITH (ONLINE = ON)` (which exists from 2016) can rewrite the column under Sch-M; widening varchar/nvarchar/varbinary to a longer fixed length (same nullability and collation) is metadata-only and not reported when the old definition is known (earlier migrations or `--schema`); when it is not known the finding says so. With ONLINE on Enterprise it is a warning: a second copy of the column doubles space and log | New column, backfill, switch readers, drop later; ONLINE off-peak with a `LOCK_TIMEOUT` | Changing a type in place on a busy table |
| `mssql-index-offline` | error | `CREATE INDEX`, `ALTER INDEX ... REBUILD`, `ALTER TABLE ... REBUILD` and `ADD PRIMARY KEY/UNIQUE` on an existing table without `WITH (ONLINE = ON)` lock writes for the whole build (a clustered key rebuilds the table). Standard and Express have no online build | `WITH (ONLINE = ON)` on Enterprise; `REORGANIZE` (always online); a window or a small table elsewhere | Building an index on a hot table at noon |
| `mssql-online-unsupported-edition` | error | `ONLINE = ON` and `RESUMABLE = ON` are Enterprise features (SQL Server 2022 and 2025 edition tables): on Standard or Express the statement fails at once | Drop the option and plan the window, or pass `--edition enterprise` when production is Enterprise | Testing on Developer and shipping to Standard |
| `mssql-lock-timeout` | warning | DDL on an existing table waits for its schema lock without a limit behind any open transaction, and every later query queues behind it. `WAIT_AT_LOW_PRIORITY` (2014+, online rebuild and SWITCH) also counts; setting it after the first DDL does not | `SET LOCK_TIMEOUT 5000` before the first DDL; retry with backoff | A long timeout so it does not fail |
| `mssql-constraint-with-check` | error | A new FOREIGN KEY or CHECK on an existing table is validated against every row (WITH CHECK is the default), holding Sch-M while it scans | `WITH NOCHECK`, then `WITH CHECK CHECK CONSTRAINT` in a later step | Adding the constraint in the same migration as the table change |
| `mssql-constraint-nocheck` | warning | `WITH NOCHECK` leaves the constraint untrusted: the optimizer ignores it and old rows may violate it | Validate it later with `WITH CHECK CHECK CONSTRAINT`; allow this finding naming that step | Leaving it untrusted for good |
| `oracle-add-column-default` | error | Oracle before 12.1: adding a nullable column with a DEFAULT writes the default into every row (full-table update, row locks, redo). NOT NULL with a DEFAULT is metadata-only since 11.1; from 12.1 both are | `ADD ... NOT NULL DEFAULT`, or add plain, backfill in batches, set the default after | A nullable column with a default on a big 11g table |
| `oracle-ddl-lock-timeout` | warning | Oracle does not queue DDL: with any open transaction on the table it fails at once with ORA-00054. The risk is a half-applied deploy, since every DDL commits | `ALTER SESSION SET DDL_LOCK_TIMEOUT = 30` before the first DDL, and re-run on failure | Assuming the DDL waits |
| `oracle-ddl-commits-dml` | warning | A DDL commits the transaction, so DML written before it in the file is committed and a later failure does not roll it back | `COMMIT` on purpose before the DDL, or put the DML in its own migration | Mixing a backfill and a DDL expecting one rollback |
| `oracle-index-not-online` | error | `CREATE INDEX` and `ALTER INDEX ... REBUILD` on an existing table without `ONLINE` block DML for the whole build | `ONLINE` on Enterprise Edition; a window or a small table on SE2 | Building an index on a hot table at noon |
| `oracle-online-unsupported-edition` | error | `ONLINE` index builds, `MOVE ONLINE` and `DBMS_REDEFINITION` are Enterprise Edition features (Licensing Information, High Availability table): SE2 fails with ORA-00439. Oracle Free has them, so a rehearsal on Free passes and production fails | Drop the option and plan a window, or pass `--edition ee` when production is EE | Rehearsing on Free and shipping to SE2 |
| `oracle-constraint-validate` | error | A new FOREIGN KEY or CHECK validates every row while it blocks DML | `ADD ... ENABLE NOVALIDATE`, then `MODIFY CONSTRAINT ... VALIDATE` in a later step (it does not block DML) | `ADD CONSTRAINT ... FOREIGN KEY` on a big table |
| `oracle-drop-column-rewrites` | warning | `DROP COLUMN` rewrites every row while it blocks DML (on top of the data loss `drop-column` reports) | `SET UNUSED` (`ONLINE` from 12c where the edition has it); drop unused columns in a window or never | `DROP COLUMN` on a big table at peak |
| `oracle-missing-slash` | error | A PL/SQL block or `CREATE PROCEDURE/FUNCTION/TRIGGER/PACKAGE/TYPE` without `/` on a line of its own: SQL*Plus and Flyway keep reading and the next statements become part of the block | `/` alone on the line after the block | Ending a procedure with `END;` only |
| `db2-reorg-pending` | error | Db2 LUW: DROP COLUMN, SET/DROP NOT NULL and SET DATA TYPE (except widening a VARCHAR, VARGRAPHIC or VARBINARY) put the table in REORG-pending state: most operations on it fail with SQLSTATE 57007 until a classic offline REORG TABLE completes | `CALL SYSPROC.ADMIN_CMD('REORG TABLE t')` right after, in the same migration | Dropping a column and assuming the table is usable |
| `db2-reorg-offline` | warning | A classic REORG TABLE rewrites the table and blocks writers while it runs; after a REORG-recommended operation it is the only way out (INPLACE is not allowed) | Run it in a window sized from a rehearsal; allow this finding naming the window | Running it at peak |
| `db2-reorg-limit` | error | At most 3 units of work with REORG-recommended operations are allowed on a table before a REORG is required (SQLSTATE 55019); several in one unit of work count once. The count runs across the migrations of the run | A REORG between the groups, or group the operations into one unit of work | A fourth ALTER of this kind without a REORG |
| `db2-constraint-check` | error | A new FOREIGN KEY or CHECK on an existing table evaluates every existing row at once (SQLSTATE 23512 on a violation) | A query that proves the rows first, `NOT ENFORCED` when the application guarantees it, or `SET INTEGRITY` in a window | `ADD CONSTRAINT ... FOREIGN KEY` on a big table at peak |
| `db2-lock-timeout` | warning | LOCKTIMEOUT defaults to -1 (wait without limit): DDL on an existing table waits behind any open transaction and every later query queues behind it | `SET CURRENT LOCK TIMEOUT 5` before the first DDL; retry on failure | Waiting forever |
| `missing-lock-timeout` | warning | Waiting for its lock, the ALTER queues every later query behind it: a 1 ms DDL becomes a minutes-long outage. `SET LOCAL`, `SET SESSION` and `set_config` count; setting it after the first ALTER does not | `SET lock_timeout = '5s'` (and `statement_timeout`) before the first ALTER; retry with backoff | A long timeout so it does not fail |
| `concurrently-in-transaction` | error | PostgreSQL rejects `CONCURRENTLY` inside a transaction: an explicit `BEGIN`, or a runner that wraps the file | Own file in the runner's no-transaction mode: goose `-- +goose NO TRANSACTION`, dbmate `-- migrate:up transaction:false`, Atlas `-- atlas:txmode none`, Flyway `executeInTransaction=false`, Django `atomic = False`; golang-migrate and Prisma only when the file has one statement | Removing `CONCURRENTLY` |
| `transaction-conflict` | warning | The runner already wraps the file: a nested `BEGIN`/`COMMIT` ends the transaction early (SQLite: error, "cannot start a transaction within a transaction"), and `PRAGMA foreign_keys` is a no-op inside a transaction so a rebuild's `DROP TABLE` still runs `ON DELETE CASCADE` and `SET NULL` on child rows (error when the file rebuilds a table; reported once per file, covers implicit-transaction runners such as Prisma) | No `BEGIN`/`COMMIT` in the file; run a rebuild in the runner's no-transaction mode, where `PRAGMA foreign_keys=OFF` takes effect. `PRAGMA defer_foreign_keys = ON` only helps plain `NO ACTION` foreign keys. Rehearse with real child rows | `PRAGMA foreign_keys=OFF` inside a wrapped file, or `defer_foreign_keys` against cascades |
| `not-atomic` | warning | Several statements outside any transaction: a failure halfway leaves the schema between versions | `BEGIN`/`COMMIT` (PostgreSQL, SQLite, SQL Server, Db2; MySQL and Oracle DDL auto-commits, so there it is one DDL per migration and no finding). Not reported when the runner wraps the file: pass `--runner` or add its config file so the linter knows | Splitting by hand and hoping |
| `unsupported-separator` | warning | The file uses `GO` (SQL Server), `/` (Oracle) or a custom terminator (Db2 `--#SET TERMINATOR`, Liquibase `endDelimiter`) and the runner sends the file to the driver whole: the separator reaches the server as a syntax error | A runner that splits on it (see [runners.md](runners.md)), or apply the file with sqlcmd, SQL*Plus or the Db2 CLP | Leaving `GO` in a goose, dbmate or golang-migrate file |
| `missing-down` | warning | No tested way back. Only for runners that have downs; Prisma, Drizzle, Flyway Community and Atlas have none | A down that runs (tested up, down, up), or `-- migration-lint: irreversible -- <recovery plan: backup, PITR>`. In the expand phase the rollback is redeploying the previous code | A down that "drops everything" untested |
| `applied-migration-changed` | error | A file that exists in the base was edited, renamed or deleted: environments that ran the old one never run the new one, checksums fail (Flyway, Atlas, Prisma). Manifests (`_journal.json`, `atlas.sum`, `migration_lock.toml`, master changelog, Flyway `R__`) may change | Restore the file from the base; write the correction as a new migration | `flyway repair`, `liquibase clear-checksums`, `atlas migrate hash`, `prisma migrate resolve`, `alembic stamp`, deleting history rows: only by a person, recorded |
| `out-of-order` | error | A new migration sorts before the base's newest: strict runners skip or reject it on environments already past it. Warning for runners that apply older pending files (dbmate); not checked for graph runners (Django, Alembic, Liquibase) | Renumber or regenerate the branch's migration on top of the base's | Renumbering the base's |
| `duplicate-sequence` | error | Two migrations share a version (`V1` and `V1_0` are the same Flyway version) | Renumber the branch's one | "Keep both" in the merge |
| `invalid-directive` | warning | A `migration-lint:` comment that is not at the start of its comment, names an unknown rule, gives no reason, or an `irreversible` with no plan; it silences nothing | Fix the comment | Prose that mentions the directive |
| `unlinted-migration` | warning | A new migration that is not SQL (Python, JS) was not read | Lint the SQL its runner produces: pipe it to `migration-lint.mjs -` | Treating the run as a pass |
