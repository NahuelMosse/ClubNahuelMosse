# OWASP ASVS 5.0 · nivel 2 (level 2) · ClubNahuelMosse

Matriz de verificación de seguridad del repo: el nivel 1 (70 requisitos) y los 183 que agrega el nivel 2, 253 en total, como los
publica OWASP. El repo elige el nivel 2 (L2) porque la app guarda datos personales (DNI, fecha de nacimiento, correo) y permisos
(socio y administrador). Describe `main`. Los números de hallazgo remiten a la revisión de la rama `kit-3` (`specs/REVISION-kit3.md`); las filas
que las cards REV-01 a REV-08 corrigieron están `meets` con su test, y las que siguen `fails` dicen por qué y quién lo decide.

**Cómo se responde cada fila**, con uno de cuatro estados y su evidencia:

| Estado | Cuándo | Evidencia |
|---|---|---|
| `meets` | se probó o se midió y se cumple, o el código lo hace de forma que no admite otra lectura | el test, el archivo y la línea, o el comando |
| `fails` | no se cumple | qué pasa, el hallazgo de la revisión y la card que lo corrige; si no figura en la revisión, dice que no tiene card |
| `not verified` | no se pudo comprobar | por qué; no cuenta como cumplido |
| `not applicable` | la funcionalidad no existe en este producto | la razón sale del requisito |

**V15.1.1** exige plazos de remediación para los componentes con vulnerabilidades. Los plazos los decide una persona y todavía no
hay respuesta: la fila queda `fails` hasta entonces (REV-07-ASM-06).

La API es JSON para una app nativa: no usa cookies ni sesiones propias (el portador es el ID token de Firebase), no acepta
archivos y no implementa WebSocket, OAuth, SAML ni WebRTC. La identidad (cuentas, contraseñas, tokens) es de Firebase
Authentication como servicio gestionado. El despliegue en Render no se hizo (revisión, «Cobertura sólo nominal»), así que lo que
depende de la plataforma queda `not verified`.

*Fuente: OWASP Application Security Verification Standard 5.0.0, `https://github.com/OWASP/ASVS`, licencia CC BY-SA 4.0. Texto de
los requisitos sin modificar.*
